# KTSGServer 世界层 TCP 与 PVP 层 UDP 架构规划

这份文档整理当前已经明确下来的服务端目标，用来替代之前偏“登录后直接进房间”的理解。

核心结论只有一句：

- 登录后玩家先进入世界层，世界层只走 TCP
- 只有玩家主动进入 PVP，并且房间准备完成后，才创建战斗实例并启用 UDP

## 1. 总体目标

服务端分成两层：

- 世界层
  - TCP 常驻
  - 负责登录、账号、背包、装备、武器、商店、聊天、任务、匹配申请等非战斗事务
  - 玩家在世界层中的移动和普通战斗不做服务端同步
  - 可以理解为“单机主逻辑 + 服务端持久化确认”
- PVP 战斗层
  - 只有进入 PVP 时才创建
  - 房间人齐并准备完成后才启用 UDP
  - UDP 负责移动、输入、属性、动作、伤害、快照等战斗逻辑
  - 战斗结束后销毁实例并回到世界层

这意味着：

- TCP 是常驻基础连接
- UDP 是战斗期的临时连接
- `RoomSession` 和 `BattleSession` 不是一个概念

## 2. 两层世界的职责边界

### 2.1 世界层职责

世界层只处理持久化相关和非战斗业务。

建议放在世界层的内容：

- 登录 / 登出
- 拉取玩家资料
- 背包、货币、商店、奖励
- 装备穿脱
- 武器切换
- 养成、加点、强化
- 聊天
- PVP 匹配、组队、邀请、准备

世界层不做的内容：

- 玩家位置权威同步
- 普通探索实时移动同步
- 战斗输入同步
- 实时战斗伤害裁定

所以世界层本质上是：

- 以 TCP 为中心的在线服务层
- 以持久化和事务处理为主

### 2.2 PVP 战斗层职责

战斗层只在 PVP 中出现。

建议放在战斗层的内容：

- 战斗房间实例化
- 战斗角色初始化
- 输入同步
- 移动同步
- 角色属性运行时计算
- 动作播放和 `PlayAction`
- buff
- 伤害结算
- 战斗快照
- 战斗结束结算

战斗层本质上是：

- 以 UDP 为中心的权威同步层
- 以 Tick、快照和状态裁定为主

## 3. 生命周期流程

## 3.1 连接与登录

1. 客户端启动后连接 TCP
2. 服务端创建 `PlayerSession`
3. 客户端发送 `ReqLogin`
4. `LoginService` 校验账号
5. 服务端把 `PlayerSession` 标记为已登录
6. 客户端进入世界层

此时状态：

- 有 TCP
- 没有房间
- 没有 UDP
- 没有战斗实例

## 3.2 世界层在线阶段

此阶段玩家只是“在线”，不是“在战斗里”。

客户端可以通过 TCP 发送：

- 获取玩家数据
- 获取背包
- 装备切换
- 武器切换
- 商店购买
- 聊天
- 进入匹配

此阶段不创建 `RoomSession`，更不创建 `BattleSession`，除非玩家明确进入 PVP 流程。

## 3.3 进入 PVP 准备阶段

玩家选择 PVP 后，才开始房间逻辑。

流程建议是：

1. 玩家发起匹配或创建房间
2. 服务端创建 `RoomSession`
3. 玩家加入房间
4. 选择角色 / 装备锁定
5. 玩家 Ready
6. 房间检查人数、准备状态、开局条件

此时仍然建议只使用 TCP。

原因：

- 房间阶段主要是组织和确认
- 还没有真正进入战斗
- 没必要提前建立 UDP 连接

## 3.4 战斗开始阶段

只有当房间满足开战条件时，才进入真正战斗阶段。

建议流程：

1. `RoomService` 通知 `BattleService` 创建 `BattleSession`
2. 服务端基于房间玩家生成战斗参数
3. 服务端给每个玩家签发 UDP token
4. TCP 把 token、战斗端口、battleId 发给客户端
5. 客户端根据 token 连接 UDP
6. 服务端验证 token 并绑定 UDP 到对应 `PlayerSession`
7. 全员 UDP 绑定成功后，`BattleSession` 正式开局

这条流程下：

- TCP 负责战前控制
- UDP 负责战斗期同步

## 3.5 战斗结束阶段

战斗结束后：

1. `BattleSession` 停止 Tick
2. 统计战斗结果
3. 把奖励/结算回写到世界层数据
4. 解绑 UDP
5. 销毁 `BattleSession`
6. 玩家回到世界层在线状态

此时：

- TCP 仍在
- UDP 关闭
- 房间可以销毁，也可以回到准备态，取决于玩法设计

## 4. 核心对象职责

## 4.1 PlayerSession

`PlayerSession` 是在线玩家的会话对象。

建议负责：

- TCP 连接
- 登录态
- `AccountId / PlayerId`
- 是否在房间中
- 是否在战斗中
- 当前绑定的 UDP 连接
- 最后活跃时间

建议不要负责：

- 完整 Mongo 文档
- 完整战斗属性计算
- 房间全局逻辑

它更像“在线玩家上下文”。

## 4.2 RoomSession

`RoomSession` 是 PVP 开战前的组织容器。

建议负责：

- 房间号
- 房主
- 成员列表
- Ready 状态
- 选角和装备锁定
- 是否满足开始条件
- 开始游戏前的基础校验

建议不要负责：

- 真正的战斗 Tick
- 快照
- 战斗中的属性/buff/伤害逻辑

`RoomSession` 是“准备态”，不是“战斗态”。

## 4.3 BattleSession

`BattleSession` 是战斗期的真正运行时对象。

建议负责：

- Tick
- 快照
- 输入处理
- 移动同步
- 动作同步
- 属性运行时计算
- buff
- 伤害
- 结算

`BattleSession` 才应该和 UDP 强关联。

## 5. 为什么 RoomSession 和 BattleSession 必须拆开

这两个对象解决的问题不同。

`RoomSession` 解决：

- 谁能一起开局
- 什么时候开局
- 开局前配置是否齐全

`BattleSession` 解决：

- 开局后如何同步和裁定
- 战斗内的数据如何演进

如果把两者混在一起，后面会出现这些问题：

- 房间准备阶段和战斗阶段生命周期混乱
- UDP 绑定逻辑和房间状态耦合
- 战斗结束后回房间/重开局逻辑难写

所以建议从一开始就拆。

## 6. 数据分层建议

## 6.1 持久化数据

Mongo 中建议存的是来源数据和持久化状态。

建议存：

- 账号信息
- 玩家基础资料
- 背包
- 装备/武器实例
- 加点
- 货币
- 商店购买结果
- 长期养成结果

不建议直接长期存：

- 完整 `BattleSession`
- 战斗快照
- 房间运行时对象
- 大量临时派生属性

## 6.2 世界层运行时数据

世界层运行时可以缓存：

- 已登录的 `PlayerSession`
- 当前玩家面板数据
- 当前已穿装备
- 当前已装武器
- 当前养成状态

这部分服务端可以算，但重点是给事务和进入战斗前准备使用。

## 6.3 战斗层运行时数据

战斗层建议单独构建 runtime：

- 战斗角色属性板
- 当前 HP/Rage
- 当前异常累积
- 当前 buff 列表
- 动作状态
- 输入缓存

战斗 runtime 应该是从持久化数据“组装出来”的，而不是直接等同于 Mongo 文档。

## 7. 属性计算应该放在哪里

世界层和战斗层都需要一定程度的属性计算，但层次不同。

### 7.1 世界层

世界层主要需要：

- 面板属性
- 装备切换后的即时属性刷新
- 武器切换后的即时属性刷新
- 商店/养成后的结果预览

这部分可以先做简化版。

### 7.2 战斗层

战斗层必须有权威计算。

包括：

- 最终战斗属性
- buff 生效
- 伤害
- 资源变化
- 当前状态值

这部分后面做 UDP 战斗时必须补齐。

## 8. 现阶段推荐的实现顺序

按你当前目标，推荐的顺序如下。

### 阶段 1. TCP 登录常驻

目标：

- TCP 可长期在线
- 完成登录
- 完成玩家会话绑定

需要：

- `Program`
- `ServerRuntime`
- `LoginService`
- `PlayerSession`

### 阶段 2. 世界层非战斗业务

目标：

- 玩家登录后能拉数据
- 能做装备/武器/背包/商店等事务

需要：

- 玩家文档模型
- 载具和装备相关服务
- TCP handler

### 阶段 3. PVP 房间层

目标：

- 创建房间
- 加入房间
- Ready
- 角色和装备锁定

需要：

- `RoomSession`
- `RoomService`

### 阶段 4. UDP 战斗层

目标：

- TCP 下发 token
- UDP 绑定
- 战斗 Tick
- 输入/移动/动作/属性/伤害同步

需要：

- `BattleSession`
- `BattleService`
- 快照层
- 战斗属性层

### 阶段 5. 战斗结算回写

目标：

- 战斗结果回写到 Mongo
- 玩家回到世界层

## 9. 当前对 KTSGServer 的具体落地建议

基于你现在已有的 `ServerRuntime`、`PlayerService`、`RoomService`、`BattleService`，建议这样对齐：

- `PlayerService`
  - 负责世界层在线玩家
- `RoomService`
  - 只负责 PVP 准备房间
- `BattleService`
  - 只负责战斗 token、战斗实例、UDP 绑定
- `ServerRuntime`
  - 统一驱动 TCP 常驻
  - 统一驱动房间/战斗生命周期

也就是说：

- 先不要让登录直接进房间
- 先不要把 `RoomSession` 设计成战斗房间
- 让 `BattleSession` 真正承担 UDP 和战斗逻辑

## 10. 现阶段最关键的设计准则

如果压缩成几条原则，当前架构应该遵守：

1. TCP 世界层和 UDP 战斗层必须分离
2. 登录成功只表示“进入世界层在线态”，不表示“进入战斗态”
3. 房间只负责开战前组织，战斗实例才负责战斗期同步
4. 所有持久化变更都必须经过服务端确认
5. UDP 只在 PVP 战斗实例期间启用

## 11. 下一步建议

基于这份架构，最优先的实现顺序建议是：

1. 完成 TCP 登录与在线会话
2. 完成世界层玩家数据读取
3. 完成装备/武器等非战斗事务
4. 再实现 PVP 房间层
5. 最后接入 UDP 战斗层

不要反过来先做完整战斗属性板再回来补登录世界层，这样会让主链路失焦。
